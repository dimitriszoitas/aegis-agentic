# Staged migration and visible progress

Use these stages for a requested repository systemization. They organize work and evidence, not approval gates. Continue authorized work between stages; ask only when an unresolved product decision actually requires the user. Audit-only scope stops before source migration and must say so.

Maintain `docs/systemization/progress.json` (or the project's established equivalent) from the start. Each stage has `id`, `status` (`not-started`, `in-progress`, `blocked`, `complete`), evidence, remaining work and the next action. Track bounded work items with owner, source/call sites, decision, affected consumers, validation and status. A stage may be reopened by new evidence. Do not quietly narrow the original scope to make it complete.

| Stage | Work | Exit evidence |
| --- | --- | --- |
| 1. Map the whole application | Walk every project folder; classify source, packages, routes, assets, documentation, generated output and external dependencies. Read nested guidance. Find real app/server/route/public entry points, aliases, providers, flags and dynamic loading. Capture baseline checks and representative screens. | Recorded directory census and exclusions with reasons; source roots and route inventory reviewed. An unfamiliar folder is inspected, not skipped. Unsupported frameworks and inaccessible workflows are explicit open items. |
| 2. Reconcile UI and usage | Discover exported and local components, wrappers, specialized variants and inline compositions across all source folders, including features, modules, routes, pages and arbitrary reusable directories. Trace actual app usage independently of stories. | Every discovered UI source has a family/pattern/layout/product-host/support disposition or remains visibly unreviewed. APIs, defaults, state, consumers and public obligations are recorded. Imports alone never establish rendered coverage. |
| 3. Review inline UI and design decisions | Inspect inline HTML/JSX, repeated structures, styled wrappers, CVA/style maps, CSS-in-JS, utility classes, hardcoded design values and modal/list/render callbacks. Compare appearance and behavior with existing families. | Each candidate cluster has a reuse, variant, extraction, token migration, deliberate exception or investigate decision with source evidence. Existing values and intended design choices are distinguished; shared scales, group ownership and intentional exceptions are recorded. API payloads, event timing, selection placement and state ownership to preserve are captured. |
| 4. Define the migration batches | Choose canonical owners, compatibility adapters, token categories, page recipes and docs destinations. Separate reusable boundaries from domain orchestration. Prioritize shared dependencies and one representative consumer per family. | Before/after ownership, token-choice and consumer map; planned value changes distinguished from reference-only changes; concrete acceptance cases; explicit incompatible overlaps and convergence steps. Existing names and APIs retained where required. |
| 5. Implement and migrate consumers | Build or extend the actual shared implementation, its complete API and owned tokens. Migrate callers in bounded batches; retain consumed adapters. Correct verified accessibility/functional defects without silently redesigning the product. | Changed consumers import/use their canonical owner. API/state/value regressions pass for the batch. Required new capabilities have implementation, contract, exports, guidance, discovery and consumer integration. Unmigrated callers remain counted. |
| 6. Deliver the catalog | Build topic Foundations, canonical family pages, working playgrounds, patterns and layouts using real implementations. Show actual app-shell pieces. Place domain configurations and audits separately. | Every included family/variant has its source binding, documented API, direct specimen or reproducible playground setup. Controls work. Existing links preserved where feasible. Missing docs remain separate from missing implementations. |
| 7. Verify and close | Re-run discovery and usage, compare source changes and representative workflows, test shared patterns across pages, verify theme/viewport/keyboard/state behavior relevant to changes, and run affected builds/tests. | Fresh reports; no unexplained newly discovered UI; covered scope reconciled to actual consumer changes. Remaining duplication, token debt, unsupported contexts and failures remain open. Publishing status is separate. |

## Discovery commands and their limits

For React/TypeScript/JavaScript, use the portable scripts with the target's installed TypeScript:

```sh
node /path/to/aegis/skills/systemize-repo/scripts/ui-discovery.mjs --root=/path/to/product
node /path/to/aegis/skills/systemize-repo/scripts/component-usage.mjs --root=/path/to/product --entry=src/main.tsx
node /path/to/aegis/skills/systemize-repo/scripts/migration-status.mjs --root=/path/to/product
```

The first report walks the whole repository, records skipped directories/files, and finds syntax-backed candidates for local/exported UI, inline composition, structural repetition and fixed styling. Folder names do not establish component ownership. Generated files point to a generator review. Vue/Svelte/Astro/HTML templates are surfaced for a framework-aware pass, not silently called covered. Review exclusion conventions because a target may use `build` or `vendor` differently. Follow relevant symlink/workspace package targets explicitly when they are owned source.

The usage report now discovers UI throughout the tree. A supplied old inventory supplements discovery; it cannot hide newly found components. Confirm framework entry conventions and unresolved runtime registries separately. Neither report interprets every runtime branch, proves dead code, or determines a correct abstraction automatically.

After creating the progress ledger, the status command produces a compact `migration-status.json` for reporting and rejects inconsistent completion claims. Use stage IDs `map`, `inventory`, `inline-review`, `plan`, `migrate`, `catalog`, `verify`. Record the reviewed discovery `sourceHash` as `discoveryHash`; record file dispositions in `review.files` with `file`, `decision` and `evidence`, and candidate decisions in `review.findings` with `id`, `decision` and `evidence`. Evidence is a reference to actual review or checks, not generated proof. Missing dispositions stay open. The usage analyzer records `discoverySourceHash` for the discovery snapshot it actually inspected. The status checker validates that link separately from the reviewed discovery hash and refuses verification completion with missing or stale usage linkage. Older usage reports must be regenerated. Do not compare the reports’ `sourceHash` fields directly: usage fingerprints scripts, while discovery also includes styles and templates. `discoverySnapshotCurrent` and `usageSnapshotCurrent` expose each check; `snapshotCurrent` requires both. These are source-snapshot checks, not proof that entry-point choices or compiler configuration were reviewed; rerun usage after changing either. The checker also detects newly discovered sources, undecided findings and completed stages that still list remaining work; it cannot judge whether a human/agent's evidence is sound.

## Inline UI review

Hardcoded means both design decisions embedded in styling and UI responsibilities repeated inside hosts. A repeated native button, selectable modal row, custom empty state, toolbar, card, status badge or input wrapper may need an existing component, a supported variant or a new reusable boundary. It may also be a deliberate small host composition. Inspect it even if it has no exported PascalCase name and no adjacent story.

For each candidate, compare real anatomy and behavior before editing. Preserve leading/trailing indicators, hit targets, single versus multi selection, disabled behavior, keyboard/focus, immediate versus draft commit, submit/cancel, API payloads, permissions and responsive behavior. Repeated JSX shape is only a discovery signal. A class such as `p-4` may already resolve through a configured token; inspect its definition rather than blindly replacing it. Static pixels can be intentional primitive values; measured dimensions and content values are runtime data. Never lower the literal count by hiding values in another file or adding aliases without correct ownership.

When an existing component lacks the required treatment, add a variant only if the responsibility/state model matches. Retain the consumer API through an adapter when necessary. Build a separate component or pattern for distinct semantics. Verify the caller after replacement, not just the new Storybook fixture.

## Token architecture review

Within stages 3–5, reconcile every included foundation family against the shared contract. Review primitive types and exact values, shared semantic choices and ordering, group ownership and application, four mappings, compatibility aliases and actual consumers. Record duplicate choices, wrong-tier responsibilities, intended exceptions and any planned visual changes. A renamed token or a passing dependency check alone cannot close this review. Verify the resulting role map in source and Foundations, then test the affected UI.

## Progress that reflects outcomes

Report concrete denominators with scope, not an invented overall percentage: directories inspected/requiring review, UI sources classified/unreviewed, canonical families with API and variant evidence, consumers migrated/remaining, candidate clusters decided/open, token consumers verified/pending, and workflows checked/unverified. Count source files, component families and story examples separately.

Show the current stage, current batch, completed work, unresolved findings and next step in user updates and in a discoverable migration progress page when Storybook is delivered. Keep the same ledger between runs. A report regeneration updates facts; it must not automatically mark review or migration items complete. A large story count, passing build or tidy sidebar cannot close stages 2–5.

At handoff, report the original requested scope and each stage's actual status. If work remains, say what remains and preserve the resumable next batch. Do not label the full skill successful merely because one pilot or documentation batch passed.
